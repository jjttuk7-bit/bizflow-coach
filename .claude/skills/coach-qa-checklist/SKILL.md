# 코치 통합 정합성 검증

신규 코치 모듈의 경계면을 교차 검증하는 절차.

이 프로젝트에서 런타임 결함의 대부분은 코드가 틀려서가 아니라 **두 곳이 서로 어긋나서** 발생한다. 프롬프트도 완벽하고 컴포넌트도 완벽한데, 프롬프트의 출력 형식과 렌더러의 기대가 다르다. 각각을 따로 보면 둘 다 정상이다.

**"존재 확인"은 검증이 아니다. "교차 비교"가 검증이다.**


> **하위 스킬 안내:** 이 스킬은 `bizflow-coach-builder` 오케스트레이터가 담당 에이전트를 통해 호출하는 하위 스킬이다. 사용자가 코치 추가·수정을 요청했는데 오케스트레이터가 아직 실행되지 않았다면, 이 스킬을 단독으로 쓰지 말고 `bizflow-coach-builder`를 먼저 호출하라. 단독 실행하면 다른 경계면이 어긋난 채로 끝난다.

## 왜 정적 타입 검사로 못 잡나

| 우회 경로 | 결과 |
|---|---|
| `callGemini`가 `Promise<string>` 반환 | 프롬프트가 무엇을 출력하든 타입 통과. 출력 형식 불일치는 컴파일러가 절대 못 잡는다 |
| dispatch switch가 **문자열** 비교 | 코치 이름 오타·누락을 컴파일러가 못 잡는다. default로 조용히 빠진다 |
| `JSON.parse` 결과 캐스팅 | responseSchema와 TS 타입이 달라도 통과 |
| 두 파라미터가 모두 `string` | 인자 순서가 바뀌어도 통과 |

`npm run build` 통과는 "동작한다"의 근거가 아니다.

## 검증 방법: 양쪽 동시 읽기

한쪽만 읽고 "정상으로 보인다"고 판정하지 않는다. 반드시 생산자와 소비자를 **같이 열어놓고** 대조한다.

---

## 경계면 1 — 출력 형식 ↔ 렌더러

| | |
|---|---|
| 생산자 | `geminiService.ts`의 `format*Prompt` → `# 출력 형식` 섹션 |
| 소비자 | `components/MarkdownRenderer.tsx:111` — `line.startsWith('### ')` |

**절차:**
1. 프롬프트의 `# 출력 형식`에서 최상위 섹션 헤딩을 모두 추출한다
2. 각 헤딩이 `### `(샵 3개 + 공백)로 시작하는지 확인한다
3. 하위 제목이 `####` 또는 `**굵게**`인지 확인한다 (`### `로 시작하면 의도치 않게 별도 아코디언이 된다)
4. 섹션 수가 3~5개인지 확인한다

**판정:**
- `### ` 헤딩 없음 → **실패**. 결과가 통짜 텍스트로 렌더된다
- 하위 제목이 `### ` → **실패**. 아코디언이 과분할된다
- `### ### ` 이중 표기 → **미검증**. `substring(4)` 이후 제목에 `###`가 남지만, Gemini가 이 표기를 어떻게 정규화하는지는 실제 응답을 봐야 안다. 기존 코치 전체가 이 표기를 쓰므로 신규 코치만 문제 삼지 말고 리더에게 "전체 확인 필요" 항목으로 보고한다

---

## 경계면 2 — 서비스 시그니처 ↔ 핸들러 호출

| | |
|---|---|
| 생산자 | `geminiService.ts`의 `export const get*` 파라미터 목록 |
| 소비자 | `App.tsx`의 `handleAnalyze*` 또는 `action` 내부 호출부 |

**절차:**
```bash
grep -n "export const get{Name}" -A 6 services/geminiService.ts
grep -n "await get{Name}(" App.tsx
```
1. 파라미터의 **개수·순서·타입**을 하나씩 대조한다
2. `Promise<T>`의 `T`가 `string`인데 호출측이 객체 필드에 접근하지 않는지 확인한다
3. 반대로 `T`가 객체인데 호출측이 `setAnalysisResult(result)`에 그대로 넣지 않는지 확인한다 (`AnalysisResult`의 `result` prop은 `string | null`이다)

**흔한 실패:** 두 파라미터가 모두 `string`이라 순서가 바뀌어도 컴파일 통과. 프롬프트에 엉뚱한 값이 바인딩된다.

---

## 경계면 3 — 폼 필드명 ↔ 프롬프트 변수

| | |
|---|---|
| 생산자 | `components/{Name}Input.tsx`의 `useState` 필드명과 `onAnalyze({...})` 객체 키 |
| 소비자 | `format*Prompt`의 `# 사장님 요청 정보` 안 `${data.x}` |

**절차:**
1. 컴포넌트가 `onAnalyze`에 넘기는 객체의 키를 모두 나열한다
2. 프롬프트의 `${data.*}` 참조를 모두 추출한다
3. **양방향으로** 대조한다 — 프롬프트에만 있는 키(→ `undefined` 삽입)와 폼에만 있는 키(→ 입력이 무시됨) 둘 다 결함이다
4. 선택 입력 필드에 `|| '정해지지 않음'` 폴백이 있는지 확인한다

**흔한 실패:** `targetArea` vs `target_area`, `productInfo` vs `product`. 프롬프트에 `undefined` 문자열이 들어가고 Gemini는 그걸 정보로 취급해 엉뚱한 답을 낸다.

---

## 경계면 4 — 페르소나 이름 정합성

코치 이름이 **4곳**에 문자열로 하드코딩된다. 하나라도 어긋나면 기능이 조용히 죽는다.

| 위치 | 파일 | 어긋나면 |
|---|---|---|
| Specialist 객체 `name` | `App.tsx` specialists 배열 | (기준값) |
| `collaborationBlock` 로스터 | `geminiService.ts:27` | 다른 코치가 이 코치를 추천하지 못함 |
| dispatch switch case | `App.tsx:335` (아키타입 B만) | 채팅이 default 문구만 반복 |
| 프롬프트 `# 역할` | `geminiService.ts` `format*Prompt` | 답변 속 이름과 카드 이름이 달라 신뢰 붕괴 |

**절차:**
```bash
grep -n "{코치 이름}" App.tsx services/geminiService.ts
```
글자 하나까지 일치하는지 본다. 공백, 슬래시(`계약/노무 코치 솔로몬`), 괄호(`우리 가게 성장 파트너 (HR)`)까지 포함한다.

**아키타입 B는 최소 4곳, 그 외는 최소 3곳**에서 결과가 나와야 한다.

---

## 경계면 5 — AppStage 값 정합성

stage 문자열이 **최대 4곳**에 등장한다.

| 위치 | 파일:라인 | 어긋나면 |
|---|---|---|
| `AppStage` 유니온 타입 | App.tsx:63 | TypeScript 에러 (유일하게 컴파일러가 잡아줌) |
| `action`의 `setStage()` | specialists 배열 | 존재하지 않는 화면으로 이동 |
| `renderContent()` case | App.tsx:900~ | **흰 화면 또는 default(프로필 설정)로 튐** |
| 채팅 greeting useEffect | App.tsx:95 (아키타입 B만) | 인사말 없이 빈 채팅창 |

**절차:**
```bash
grep -n "'{stage-value}'" App.tsx
```
아키타입 A/D는 3곳, B는 4곳에서 나와야 한다. C는 stage를 추가하지 않으므로 해당 없음.

## 점진적 실행

전체 완성을 기다리지 않는다. 누적된 뒤 잡으면 수정 비용이 몇 배가 된다.

| 트리거 | 즉시 검증할 경계면 |
|---|---|
| 프롬프트 엔지니어가 함수 완료 알림 | 1 (출력 형식), 4 (이름) |
| UI 통합자가 배선 완료 알림 | 2 (시그니처), 3 (폼 필드), 5 (stage) |
| 수정 반영 알림 | 해당 경계면 재검증 + 회귀 확인 |

## 리포트 원칙

**검증하지 못한 것을 "통과"로 보고하지 않는다.** 정적 분석으로 확정할 수 없는 항목이 반드시 있다:

- Gemini가 실제로 `### `를 출력하는가 → 실행 확인 필요
- 지식 베이스의 수치가 사실인가 → 출처 확인 필요
- 아코디언 UI가 실제로 잘 보이는가 → 브라우저 확인 필요

이런 항목은 **"미검증 + 사유 + 수동 확인 방법"**으로 남긴다. 확정할 수 없는 것을 확정했다고 보고하는 것이 QA의 가장 큰 실패다.

## 판정 기준

| 판정 | 조건 |
|---|---|
| 통과 | 경계면 5종 모두 통과, 미검증 항목이 실행 확인 수준 |
| 조건부 통과 | 결함 없으나 미검증 항목이 기능에 영향 가능 |
| 실패 | 경계면 1개 이상 불일치 |

## 검증 후

리포트만 쓰고 끝내지 않는다. 결함은 **발견 즉시** 담당 에이전트에게 파일:라인 + 수정 방법을 포함해 SendMessage한다. 경계면 이슈는 **양쪽 에이전트 모두**에게 알린다 — 한쪽만 고치면 다시 어긋난다.
