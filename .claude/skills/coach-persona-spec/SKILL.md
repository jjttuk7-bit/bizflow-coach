# 코치 페르소나 설계

BizFlow Coach에 신규 AI 전문가를 추가하거나 기존 페르소나를 수정할 때의 절차.

이 앱에서 사용자는 기능이 아니라 **사람**을 고른다. 대시보드에는 23명의 얼굴이 있고, 사장님은 "재고 분석 기능"이 아니라 "매니저 알렉스"를 누른다. 페르소나가 흐릿하면 기능이 정확해도 제품이 무너진다.


> **하위 스킬 안내:** 이 스킬은 `bizflow-coach-builder` 오케스트레이터가 담당 에이전트를 통해 호출하는 하위 스킬이다. 사용자가 코치 추가·수정을 요청했는데 오케스트레이터가 아직 실행되지 않았다면, 이 스킬을 단독으로 쓰지 말고 `bizflow-coach-builder`를 먼저 호출하라. 단독 실행하면 다른 경계면이 어긋난 채로 끝난다.

## 절차

### 1. 중복 검사 — 가장 먼저

[references/roster.md](references/roster.md)를 읽고 기존 23명과 역할을 대조한다.

중복도를 판정하고 다음 기준으로 결정한다:

| 중복도 | 판정 | 행동 |
|---|---|---|
| 60% 이상 | 확장 권고 | 신규 생성을 멈추고 리더에게 "기존 {코치}의 프롬프트 확장"을 역제안 |
| 30~60% | 차별화 필수 | 진행하되, 기존 코치와 무엇이 다른지 `description`에 명시적으로 드러냄 |
| 30% 미만 | 신규 생성 | 그대로 진행 |

23명은 이미 많다. 대시보드 인지 부하가 한계에 가까우므로, 새 얼굴을 추가하는 것은 기본값이 아니라 **정당화가 필요한 결정**이다.

### 2. 정체성 결정

| 필드 | 규칙 |
|---|---|
| `name` | `{역할 수식어} {한글 이름}` 형식. 예: `데이터 분석가 앤`, `공간 디렉터 노아`. 이름은 친근한 2음절 한글/외래어 |
| `role` | 명사구 한 줄. 대시보드 카드에 노출되므로 20자 이내 |
| `description` | 이 코치가 **사장님에게 무엇을 해주는지** 1~2문장. 기능 나열이 아니라 결과 약속으로 쓴다 |
| `category` | 아래 5개 중 하나. 신규 카테고리는 만들지 않는다 (대시보드 그룹핑이 깨진다) |

**카테고리 (고정):** `System` · `성장 & 전략` · `운영 & 재무` · `팀 & 법률` · `공간 전략 & VMD`

### 3. 시각 자산 배정

**Icon**: [components/icons.tsx](../../../components/icons.tsx)에 실재하는 것만 쓴다. 없는 아이콘을 지정하면 import 에러가 난다.

사용 가능 목록과 현재 점유 상태는 [references/roster.md](references/roster.md)의 "아이콘 점유 현황" 참조. `CurrencyWonIcon`은 정의되어 있으나 어떤 코치도 쓰지 않는 미사용 자산이다.

**색상**: Tailwind 색상 하나를 골라 4개 필드를 세트로 채운다.

```ts
classes: {
  border: 'border-{color}-500',
  bg:     'bg-{color}-100',
  text:   'text-{color}-600',
  nameText: 'text-{color}-600',
}
```

`bg`는 항상 `-100`으로 고정한다. 진하면 카드 안의 텍스트 대비가 무너진다. 색상이 소진되었으면 겹치는 색을 쓰되 Icon을 반드시 다르게 하여 시각적 구분을 확보한다.

### 4. greeting 작성

greeting은 `SpecialistGreeting` 화면에 전문으로 노출된다. 사용자가 이 코치와 처음 만나는 순간이다.

**구조 (2~4문장):**
1. 사장님의 상황에 공감 — "~하시죠?", "고민이 많으시죠?"
2. 이 코치가 가진 것을 제시 — 방법론, 경험, 데이터
3. 행동 유도 — 질문으로 끝낸다

**규칙:** 항상 "사장님" 호칭, 존댓말, 1인칭으로 자기 이름을 언급한다.

기존 greeting 예시는 [references/roster.md](references/roster.md)의 "greeting 샘플" 참조.

### 5. 구현 아키타입 결정 — 가장 중요

이 결정이 프롬프트 엔지니어와 UI 통합자의 작업 범위를 전부 결정한다. **입력의 성격**으로 판단한다.

| 아키타입 | 언제 | 입력 방식 | 신규 컴포넌트 | 배선 지점 수 |
|---|---|---|---|---|
| **A. 폼 입력형** | 분석에 구조화된 정보 3~4개가 필요 | 전용 `*Input.tsx` 폼 → 1회 분석 | 필요 | 6 |
| **B. 채팅형** | 대화를 주고받아야 함 | `CSCoachChat` 재사용 | 불필요 | 7 |
| **C. 즉시 분석형** | 프로필·비즈니스 데이터만으로 충분 | 입력 없음, 클릭 즉시 분석 | 불필요 | 5 |
| **D. 자체 완결형** | 다단계 흐름·자체 상태 관리 필요 | 컴포넌트가 직접 geminiService 호출 | 필요 | 4 |

**판정 질문 순서:**
1. 사장님이 여러 번 되물어야 하는 주제인가? → **B**
2. 분석 전에 사장님이 입력해야 할 정보가 있는가? → 있으면 A, 없으면 C
3. 단계별로 진행되거나 중간 산출물을 다듬어야 하는가? → **D**

아키타입 B는 코드량이 가장 적지만 배선 지점이 가장 많다(7곳). 쉬워 보인다고 방심하면 반드시 빠뜨린다.

### 6. 네이밍 계약 확정

하위 에이전트들이 이 이름들로 서로의 코드를 참조한다. 여기서 확정한 뒤 바꾸면 여러 파일이 동시에 어긋난다.

| 항목 | 규칙 | 예시 |
|---|---|---|
| AppStage 값 | kebab-case. 아키타입 A는 `-input`, B는 `-chat` 접미사 | `packaging-input`, `packaging-chat` |
| 서비스 함수 | `get{PascalCase}` | `getPackagingAnalysis` |
| 프롬프트 함수 | `format{PascalCase}Prompt` | `formatPackagingPrompt` |
| 컴포넌트 | `{PascalCase}Input.tsx` (A) / `{PascalCase}Coach.tsx` (D) | `PackagingInput.tsx` |

### 7. 출력 섹션 설계

프롬프트 엔지니어가 `# 출력 형식`을 쓸 때 쓸 아코디언 섹션 3~5개를 미리 설계한다.

각 섹션은 사장님이 **읽고 행동할 수 있는 단위**여야 한다. "분석", "결론" 같은 추상 제목이 아니라 "당장 시작할 수 있는 저비용 액션 플랜 (초기 1개월)"처럼 구체적으로 쓴다.

섹션 수는 3~5개를 지킨다. 2개면 아코디언의 의미가 없고, 6개 이상이면 사장님이 어디부터 볼지 모른다.
